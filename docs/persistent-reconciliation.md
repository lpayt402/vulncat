## Data and matching

The additive schema preserves existing asset UUIDs, scanner imports, findings and reports. It introduces immutable source observations, source instances, native IDs, vulnerability occurrences, coverage observations, import batches, file/row locators, decisions and assignment versions. Only the current assignment projection and singleton mutation revision are mutable. Database triggers enforce immutable evidence and history; ORM guards provide an earlier error. No legacy data is backfilled or rewritten.

Nessus observations retain ReportHost attributes and complete HostProperties trees separately from normalized fields, including unknown names, repeated properties and their attributes/text. These raw values enter fingerprints; they do not become trusted identity fields. Existing saved observations are immutable and are not rewritten; reimport after this correction creates fingerprints carrying the richer raw evidence. Every observation retains raw source evidence, normalized fields, source/instance/native ID type, parser and mapping versions/hashes, filename/file hash/row number, imported time and separately supplied source observation time. Unknown time stays unknown. Event fingerprints deduplicate normalized events; every supported repeated row retains another locator. The same import request key and exact payload/actor return the immutable original result, including after a parser change. A changed payload or actor with that key returns HTTP 409. Reimport never overrides an analyst assignment, rejection or defer decision.

Matching uses indexed evidence and deterministic explanations. Native IDs are scoped by source, instance and object type. Hardware/native IDs can support an automatic assignment only when fresh, unique and free of observed conflicts. IP, hostname, shortname and MAC hits require review. Historical conflicts include unassigned evidence until an analyst rejects it; a rejected replay cannot reactivate it. IP scopes, stale/unknown/future timestamps, reused DHCP addresses, duplicate agents, reimages, aliases and conflicting IDs remain explicit uncertainty. A separate provisional asset means no safe existing match was established.

Vulnerability occurrences retain source-native status and occurrence identity without translating absence into resolution. Failed, unreachable, DNS-failed, partial and successful coverage are separate evidence. Importing failed coverage or a later file without an asset does not retire assets, change scanner finding statuses or imply remediation. These observations are not yet aggregated into the legacy scanner report or lifecycle engine.

## Decisions and transaction boundaries

Assign also corrects a wrong assignment. Create groups selected unassigned evidence on a separate asset; split moves selected evidence from one source into a new asset. Merge moves all current persistent evidence from the source to an active target. Neither operation deletes asset records or moves legacy findings. Reject retains raw evidence while removing it from matching; defer retains it for later review.

Each change appends actor, time, reason and before/after assignment versions in the same transaction as the current projection and audit record. An undo appends inverse versions; it never erases history. It refuses if an affected version changed, an asset being restored is inactive, or the operation was already undone. Unrelated subsequent imports remain intact. Import and undo operations cannot themselves be undone. Legacy asset retirement through merge or split undo is refused when current persistent evidence would be stranded.

All persistent writers, legacy import processing and legacy identity writes acquire the singleton database mutation lock first. PostgreSQL serializes writers; expected revision and per-observation versions reject stale or conflicting decisions. Actor/payload-bound request keys make retries replay safely. Preview and save share the same ordered matching plan, including durable history, unresolved conflicts and retained analyst decisions. A repeated fingerprint previews as `retain`, including its current status/version. UI saves carry a signed, actor/files/options-bound preview context and expected revision; matching uses the preview evaluation time for up to 30 minutes. Any intervening persistent or legacy identity/import commit requires a new preview. Completed batch retries replay before preview expiry checks. Direct API imports may omit preview context and then compute a fresh plan under the same mutation lock. Provisional `preview:` candidate IDs refer only to assets proposed within that bundle; save allocates durable UUIDs. Mutable projection reads explicitly refresh cached ORM values. Reads capture revision before fetching a page, so an intervening commit conservatively invalidates a decision. This bounds correctness; it does not promise concurrent ingestion throughput.

## Upgrade, rollback and restoration

Revision `0002_persistent_reconciliation` has frozen table definitions and does not edit historical revision 0001. It creates missing additive tables, validates existing columns/types/lengths, primary keys, unique/check/FK constraints and indexes, then installs immutability triggers. This also accommodates a fresh installation where 0001's historical dynamic create-all already created the new tables.

Before upgrading a real installation, stop writers, take a verified database backup and retain the previous application image. Test the upgrade on a restored copy. The CI PostgreSQL job exercises populated legacy upgrade and preserves legacy snapshots. An empty additive schema can downgrade without altering legacy data. A populated downgrade deliberately refuses; deleting evidence to force it through is unsupported. Migration table locks prevent an ingestion commit from racing the emptiness check and DROP.

For a populated installation, retain the additive tables and use the tested backup restoration procedure on a separate database before replacing an installation. A restored backup predating this increment necessarily excludes later imports and decisions; preserve a current backup as well. An older application does not enforce the new assignment guards, so do not run its writable identity workflows against new persistent evidence. CI checks a full PostgreSQL dump/restore into a separate disposable database and compares table contents and restored immutability.

## Bounded processing and validation

Imports are synchronous and bounded to 8 nonempty files, 10 MiB each, 30 MiB combined, 100,000 logical rows and 64 MiB of expanded normalized evidence across all staged rows. The expansion bound rejects the whole bundle before any writes, rather than discarding raw evidence. Bad supported-format rows produce counted errors with a sample of 50; invalid configuration or unreadable documents reject the whole import. Database-bound identifiers/statuses/hostnames have length and NUL validation, so a malformed row cannot abort PostgreSQL inserts for later supported rows. Lookups and inserts use groups of 500. Evidence and audit pages default to 50 and cap at 500; details cap locator/history samples at 200 and show totals.

The reproducible [SQLite benchmark](../scripts/validation/benchmark_persistence.py) uses 5,000 assets, 15,000 distinct observations, 100 duplicate rows and 25 malformed rows, then a reordered reimport and an end-of-list 50-item page. On Windows / Python 3.12, the final local run measured 29.876 seconds and 197.59 MiB peak Python allocations for the first import with tracemalloc enabled (223 SQL statements). The reordered repeat took 5.156 seconds without tracemalloc (72 statements), created zero observations and retained all supported locators. The 50-item page, including asset names, took 0.059 seconds (3 statements). This is one local synthetic measurement, not production PostgreSQL throughput. PostgreSQL CI additionally imports and reimports 5,000 observations and exercises real concurrent transactions.

Hosted browser QA runs the production frontend and real API with Chromium and a disposable PostgreSQL database. It checks setup, preview/save, provenance/history, assignment, correction, split, merge and undo. Trace and screenshot artifacts contain only synthetic CI data. Source fixtures remain honestly labeled synthetic; [verified schema boundaries](offline-source-formats.md) still apply. Endpoint management exact headers, tenant-specific endpoint security envelopes, infrastructure inventory IP/interface joins and directory export conventions need further publicly verifiable schemas. Spreadsheets must currently be saved as CSV; direct XLSX is not implemented. No live source connections, probes, credentials or subscriptions are introduced.
